# Agent 系统怎么搭：五篇资料的要点和对本项目的意义（2026-11-27）

问题：店主这几天看了五篇讲 agent 系统设计的资料（四段中文视频解读，加上 Anthropic 的一篇原文）。它们对本项目哪些地方有用，哪些地方我们已经做了，哪些不适合一家店？

范围：
- 一篇有原文，即 Anthropic 的《Building always-on agents》，已读原页面；
- 一篇视频提到两项研究，已核对论文摘要和官方仓库（ACE、MemRL、Memento）；
- 其余三篇只有店主转述的视频摘要，找不到原作者，下面按摘要整理，不当作一手资料。

本项目的对照依据是 2026-11-27 当天的代码和在开发环境的实测（实测记录在 `.dev/agent-probe/`）。

## 结论先说

1. **五篇说的是同一件事：确定的事交给软件，模型只负责理解、组合和表达。** 业务一致性由后端的操作和事务保证；什么时候醒、提醒谁、能做什么，由规则和权限决定；判断标准由自己的数据攒出来，再固化进系统。换模型，这些都不会丢。
2. **本项目的底子是对的：** 操作层就是任务原语，草稿就是审批，AI 提醒就是 always-on 的骨架，GLOSSARY 和 ADR 就是关系层和规则层。
3. **实测找到三个具体缺口：**
   - 多步写操作之间的依赖只能靠模型猜，AI 把开单草稿的编号当成单号填进了结账草稿；
   - 跨对象的问题会把工具次数用完，直接报错，已经查到的结果全部丢掉；
   - 人确认草稿后，结果回不到 AI 那里。
4. **一家店的数据量撑不起自动学习**，例如按效用值选经验、自动改写手册。经验沉淀走"系统统计、人来判断、固化进代码"的路，ADR-0012 已经这样定了。

## 一、Agent 软件分层：任务原语、自由组合、安全审批

来源：中文视频摘要（店主转述）。

要点：
- 把后端 API 包成 JSON Schema 交给模型，等于让模型在运行时临时充当工作流引擎。原本开发阶段要想清楚的调用顺序、幂等、不可逆的边界，被推到了每次运行时去推理。
- 多步调用中途失败，是分布式事务问题，靠语言理解解决不了。
- 解法是**任务原语**：传客户和目标套餐，后端负责校验、执行、回滚。它描述的是"能完成什么任务"，不是"有哪些资源可以改"。
- 全部做成原语，Agent 就退化成一个自然语言菜单。所以要分三层：
  - 高频、涉及钱的走原语层；
  - 长尾需求保留细粒度接口，让 Agent 自由组合；
  - 高风险操作加权限校验和人工审批。

本项目：
- 操作层（`backend/internal/ops`）注册的每个操作都是一个业务动作，在一个租户事务里执行，没有一个是增删改查式的接口。例如 `checkout_orders`、`void_order`、`upgrade_card`。
- 工具定义取自 HTTP 请求的 schema，AI 和人走同一条路径（ADR-0001）。
- 店主已按这篇定下 [ADR-0013](../adr/0013-ai-actions-tiered-by-what-they-change.md)：
  - 不改业务数据的，AI 直接做；
  - 改数据的，AI 可以自由组合成草稿组，人整组确认，一个事务执行；
  - 高风险操作由操作声明时标明，再加一道。
  - 少数标明为低风险、能当场改回的操作，员工开口后 AI 直接执行（[ADR-0014](../adr/0014-ai-executes-low-risk-writes-directly.md)）。

实测：员工说"开单和结账一起出草稿"时，AI 把开单**草稿**的编号填进了结账的 `order_id`。系统没有拦住，因为结账草稿创建时只校验参数格式。#301 是同一个问题的另一个例子：先新建顾客、再开单。

## 二、Always-on agent：模型大多在休眠，持续运行的是外面的软件

来源：[Anthropic, Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)（2026-11-13，原文）。

五个组件，每次"醒来"是一次短的运行：

- **事件收件箱**：webhook、定时任务、后台作业都只往一张数据库表里写；按来源的唯一编号去重；处理请求要立即应答，较重的检查放到运行里做；收件箱是事实来源，进程崩了换一个 worker 重试；每个收件箱同时只有一个 worker；运行期间来的事件可以批处理。
- **定时器**：分两种，一种是 agent 给自己定的跟进期限，一种是周期任务。定时器和收件箱分开存；调度器到点只往收件箱写事件，**不直接启动运行**。
- **记忆**：放在 worker 之外的持久存储里。**只存查不回来的东西**，查得到的只存指针。分为用户指令、对用户的了解、已经告诉过用户什么、任务进度四类。定期回顾整理（原文叫 dreaming）。
- **权限**：密钥放在 agent 环境之外，由代理注入；对高风险操作用分类器筛查；**调用可以挂起**：会话停在这一步，用户批准后作为收件箱事件回来，开一次新的运行接着做。
- **发件箱**：只交结果，不播过程。一次运行只有三种结局：发一条、不发、请用户批准。消息条数要用评测去调，"先安静，再慢慢赢得用户的注意"。

本项目对照：

| 组件 | 现状 |
|---|---|
| 定时器 | 已有。`reminders.RunLoop` 按门店定时检查，每店加锁，重跑不重复（`backend/internal/reminders/runner.go`） |
| 事件收件箱 | 没有。ADR-0012 写了"业务事件表"，代码里没有；目前只有一条定时规则（昨日日结简报） |
| 记忆 | 没有。没有 agent 自己的记忆存储；业务数据都能查到，`ai_reminders` 记了发过的提醒，但不给模型看；对话只回放最近 19 条消息的文字 |
| 权限 | 有一半。草稿和三档对得上；没有"确认后接着做" |
| 发件箱 | 有一半。提醒表加观察档，有去重、冷却、每日上限、有用/没用反馈；但员工端还没有看提醒的地方，"开"档的提醒只写进表里，谁也看不到（#367 要做） |
| 后台任务 | 没有。AI 对话是同步的，关掉页面就断了 |

## 三、知识分三层：事实、关系、规则

来源：中文视频摘要（店主转述）。

要点：
- RAG 按文本相似度检索，不按业务逻辑。"供应商 A 停供会影响哪些广告"这种跨系统的链条，向量检索串不起来。
- 知识分三层：
  - 事实：当前状态；
  - 关系：对象之间怎么连；
  - 规则：计算口径和决策标准。

  处理顺序是先沿关系追到对象，再取实时事实，最后用规则算出结论。
- 落点是**往上下文里填什么**：填零散的文本片段，模型只能自己拼；填沿业务链路串好的状态和确定的判断，模型只需要表达。
- 前提是对象模型清楚、规则口径统一，这部分投入比接向量库大得多。

本项目：
- 事实：85 个读工具直接查业务库，没有向量库。
- 关系：GLOSSARY 加外键已经定义清楚。
- 规则：提成、业绩、价格、售后规则都在代码和门店设置里（ADR-0002）。AI 拿到的是算好的结果，ADR-0012 还规定金额不经模型转述。

作者说的前提，我们已经做了。

实测：问"发型师 X 下个月离职，他负责哪些顾客、有没有挂单和预约、业绩提成多少、要做哪些交接"，返回 502"AI 调用工具次数超过上限"。上限是一次对话最多调 6 次模型、每次最多 8 个工具（`backend/internal/ai/ai.go:31`）。超过上限时，已经查到的结果全部丢掉；日志里也不记调用了哪些工具。

结论：缺的是**沿关系链在代码里预先串好的汇总读操作**，不缺 RAG。只有话术、店规这类非结构化内容才需要检索，单店的量写进设置就够了。

## 四、经验沉淀：把每天的决策变成下次的依据

来源：中文视频摘要（店主转述）。

要点：
- 存了聊天记录和操作日志，不等于企业变聪明了。
- 闭环是：记录决策和当时的条件 → 追踪结果和成本 → 案例够了以后分析差异 → 写成带适用条件的策略 → 更新进 Skill 或工作流 → 继续追踪，无效就回滚。整个过程不用重训模型。
- 模型能力和企业资产要分开：经验存在自己的库里，换模型不受影响。"模型能力可以买，判断能力得自己攒。"

本项目已经在记的决策：

| 决策 | 记在哪 |
|---|---|
| AI 起草后人改了哪些参数 | `ai_drafts.original_params` 对比 `params`，加草稿事件 |
| 草稿被拒及原因 | `ai_drafts.status`、`reject_reason` |
| 售后怎么处理 | `aftersales`：修补、返工、部分退款、全退，原因，是否扣业绩和提成 |
| 服务做成什么样 | `service_records`：效果、配方、满意、一般、不满意 |
| 提醒有没有用 | `ai_reminders.feedback` |
| AI 起草的记录事后被谁改了 | 操作日志带 `draft_id`，能从业务记录反查草稿 |

缺的是"结果"这一半，即决策和之后发生的事没有连起来：
- 回访提醒发出后，顾客回来了没有；
- 售后花了多少，顾客之后还来不来；
- 配方 A 做完，后来有没有返工。

这些结果大多在订单表里，但**决策当时的条件不记下，事后就推算不出来**，比如提醒按什么条件选中了谁。

## 五、不重训模型也能变聪明：经验手册

来源：中文视频摘要（店主转述）。视频提到的两项研究已经核对：

- **经验怎么存**：[ACE, Agentic Context Engineering](https://www.alphaxiv.org/abs/2510.04618)（[官方仓库](https://github.com/ace-agent/ace)）。
  - 分三个角色：生成器负责执行，反思器负责总结，整理器用确定的代码把增量合并进手册。
  - 每条经验有独立编号和"有用 / 有害"计数，只改需要改的那一条，不整本重写，因为反复重写会丢细节。
- **经验怎么选**：[MemRL](https://arxiv.org/pdf/2601.03192) 和 [Memento](https://arxiv.org/pdf/2508.16153)。
  - 每条记忆带一个效用值，任务成败后更新；检索时把语义相似度和效用值合起来排序。

作者的两个质疑：
- **归因会错**：同一次里改了两处，可能把成功归到错的那一处上。
- **反馈不可靠**：接口返回 200 不代表数据导出完整。所以要记下当时验证了什么、适用条件是什么。

ACE 的二手评述也指出：计数只是观察，不是因果；样本少时分不清规律和噪音。

作者的判断标准：值得留下的是依赖情境、需要权衡的经验；经验要经过验证、淘汰错误，**成熟后固化成工具**，不要让记忆文件夹越堆越大。

本项目：
- **店里的 AI 不做自动改写的经验库。** ADR-0012 已经否决了"AI 自己改记忆和规则"，因为老板看不见、也查不了；而且单店样本太少，计数和效用值都是噪音。经验直接按性质固化：
  - 顾客的喜好进档案；
  - 说法和步骤进工具描述和系统提示；
  - 多步流程进后端能力；
  - 每一条都由评测用例和录像来验证。
- **"草稿被确认"不等于"AI 做对了"**，这就是"200 不等于完整"。更可靠的负反馈是：
  - AI 起草、人确认的记录**后来被撤销、改价、换人、调卡**；
  - 确认前人改过参数。
- 我们自己的开发流程（Claude 和 Codex 的 memory 目录）就是一本 ACE 式的手册：每条独立、单独更新。其中几条已经固化成工具（`gate.py` 重型锁、`scripts/ci-wait.sh`）。
  - 缺的是每条的验证条件；
  - 也没有淘汰机制，已经有做完了还留着的条目。

## 不适合本项目的

- **向量库和 RAG**：业务问题都在结构化数据里，单店的非结构化内容很少。
- **按效用值自动选经验、自动改写手册**：样本太少，老板也查不了。等多门店以后再考虑。
- **Always-on 那一套里的密钥代理**：工具在进程内调用，模型本来就拿不到密钥。
