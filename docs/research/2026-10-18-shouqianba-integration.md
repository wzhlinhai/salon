# 收钱吧接入能力调研（issue #18）

调研日期：2026-10-18。背景：店里的收款目前走收钱吧。要回答的问题是：我们自研的 Go 后端能否通过收钱吧收款、能做到什么程度，以及和 #7 定下的"微信付款码 V2 + 支付宝当面付直连"方案比，各有什么取舍。

只采信一手来源：

- 收钱吧开放平台 open.shouqianba.com（新版，含开发指南和 API 文档，每页都可以加 `.md` 后缀取原文）；
- 收钱吧旧版文档 doc.shouqianba.com/zh-cn（GitBook，包含 Q&A）；
- 收钱吧智慧门店开放平台 doc.shouqianba.com/smart-store；
- 收钱吧官网 www.shouqianba.com；
- 微信支付官方文档 pay.weixin.qq.com。

代理商网站、知乎、百度知道等二手来源一律不当作事实使用。

可信度标记：

- **【已核实】**：亲自打开一手页面读到了原文。
- **【官方文档，未实测】**：文档写了，但没有用真实终端调用验证过。
- **【推断】**：从官方事实推出来的，原文没有直接写。
- **【未找到】**：在一手来源里没找到。
- **【需店主确认】**：只有店主在收钱吧 App、商户后台或微信支付商户平台里才能查到。

---

## 一句话结论

收钱吧有面向第三方系统的支付 API（"移动支付 Web API"）。接口是 JSON 格式，签名是 MD5(body+key)，不需要证书。我们的系统可以用它扫顾客付款码、生成动态收款码，并通过回调或查单拿到结果，再用我们自己的订单号（`client_sn`）把收款对到订单上。退款、撤单、查单都有接口。

但有三处限制：

1. **开发者参数不能自助申请。** 必须通过收钱吧对接人拿到 `vendor_sn`、`vendor_key` 和 `app_id`，文档里要提供的是"开发者企业"信息。
2. **公开文档里没有对账单下载接口。** 每日结算明细和手续费要去商户后台看。
3. **付款人标识的口径要实测。** 回包里的 `payer_uid` 对应微信 `sub_openid`，`payer_login` 对应 `openid`。不上送 `sub_appid` 时，大概率只能拿到收钱吧服务商 appid 下的 openid。

如果店里的微信收款是收钱吧服务商下的"特约商户"，那么现有商户号不能由我们直接调用微信官方接口。要走 #7 的直连方案，就得另外申请一个普通商户号。

## 1. 收钱吧有没有对第三方开放的接口，单店能不能申请，费用和门槛

### 1.1 有哪些接口

- 【已核实】收钱吧开放平台（https://open.shouqianba.com/ ）目前只开放了一个业务"移动支付"，描述原文是"移动支付核心业务API，包含支付、退款、查询"。来源：`/api/v1/businesses` 返回 `{"code":"payment","name":"移动支付"}`。
- 【已核实】API 文档列表（https://open.shouqianba.com/api-docs/payment ）：
  - 基础：签到 `/terminal/checkin`、激活 `/terminal/activate`。
  - 交易：聚合二维码生成 `/upay/support/precreateQrcode`、付款码支付（B扫C）`/upay/v2/pay`、预下单支付 `/upay/v2/precreate`、WAP 跳转支付 `/gateway`、退款 `/upay/v2/refund`、查询 `/upay/v2/query`。
  - 回调：支付回调通知。
- 【已核实】撤单 `/upay/v2/cancel` 只出现在签名机制页的接口列表里（https://doc.shouqianba.com/zh-cn/api/sign.html ），新版 API 文档没有单列。
- 【已核实】旧版文档还列出了分账、订单推送等扩展能力（https://doc.shouqianba.com/zh-cn/ ）：
  - 分账的前提是"对接分账需要申请收钱吧直连商户，请联系收钱吧商务同事了解确认"（https://doc.shouqianba.com/zh-cn/api/interface/分账.html ）。
  - 订单推送 `/appPush/tradePush` 的作用是"商家自有系统的订单推送至收钱吧专门收款设备上（如T9设备等）"，设备完成收款后回调 `notify_url`（https://doc.shouqianba.com/zh-cn/api/interface/MIS.html ）。
- 【已核实】另有一个"智慧门店开放平台"（https://doc.shouqianba.com/smart-store/ ），用于读取商家授权的订单数据和接收消息推送，订单类型全是餐饮类（扫码点单、外卖、收银订单等）。原文说明："当前未开放自助注册，请与您的商务联系申请注册"，"采用项目制流程"，授权"在当前试点版本中……由收钱吧开发人员手动推送授权"。【推断】这个平台面向餐饮的智慧门店产品，和我们的需求关系不大，不作为方案。

### 1.2 谁能接、怎么申请

- 【已核实】收钱吧对"开发者 (vendor)"的定义是"开发对接收钱吧API角色，一般是品牌商户或者ISV"（https://doc.shouqianba.com/zh-cn/definition.html ）。新版写法是"对接收钱吧API的主体，通常是品牌商户或系统开发团队，持有`vendor_sn`和`vendor_key`"（https://open.shouqianba.com/docs/payment/65 ）。
- 【已核实】申请方式（https://doc.shouqianba.com/zh-cn/business.html ）：向"负责对接的收钱吧技术支持同事"提供以下资料，用来"申请开通开发者参数(vendor_sn、vendor_key)和app_id"：
  - 开发者企业名称、开发者企业地址；
  - 联系人、电话、**企业邮箱**；
  - 开发语言。
- 【已核实】开放平台不能自助注册。登录页只接受"开发者序列号 (vendor_sn) / 开发者密钥 (vendor_key)"登录（https://open.shouqianba.com/login ），所以必须先从收钱吧拿到参数。商务和技术方案咨询电话是 400-886-9999 和 KA@shouqianba.com（https://doc.shouqianba.com/zh-cn/ ）。
- 【已核实】资料来源分工（https://open.shouqianba.com/docs/payment/106 ）：
  - `vendor_sn`、`vendor_key`、`app_id`、测试激活码由"收钱吧提供"；
  - 正式激活码"上线前由收钱吧或商户后台提供"。
- 【已核实】激活码"需要在商户平台门店下生成"，是"将收款设备和收款商户门店进行绑定的关键参数"（https://doc.shouqianba.com/zh-cn/definition.html ）。
- 【推断】接入是两层结构：
  - **开发者层**：我们作为开发者（ISV）申请一套 vendor 参数，一次即可。
  - **门店层**：每家店在自己的收钱吧商户后台生成激活码交给我们，我们用它激活出终端。
  这个结构天然支持多租户：以后其他用收钱吧的门店，也只需要提供激活码。
- 【未找到】一手文档没有写明单个商户（个体户）能不能以自己的名义申请开发者参数。申请表要求的是"开发者企业"信息和企业邮箱。【推断】最稳妥的做法是以我们的公司或团队主体申请；如果以门店自己名义申请，要先问收钱吧对接人是否接受。
- 【未找到】一手文档没有公布 API 接入费、年费或技术服务费，也没有公布交易费率。网上流传的 0.38% 等数字都来自代理商网站，不采信。费率按店主签约为准，见第 7 节。

### 1.3 测试环境

- 【已核实】"测试和正式业务通常使用相同API域名，不能通过更换域名区分环境"，"支付测试会产生真实交易，测试完成后应按原交易发起退款"（https://open.shouqianba.com/docs/payment/106 ）。也就是说没有沙箱，要用测试激活码对应的测试门店做真实小额交易，测完退款。
- 【已核实】国内接入域名是 `https://vsi-api.shouqianba.com`（https://doc.shouqianba.com/zh-cn/api/sign.html ）。

## 2. 能否由我们的系统发起收款，并收到结果回调、关联订单

### 2.1 终端模型

- 【已核实】调用链（https://open.shouqianba.com/docs/payment/65 ）：用 `vendor_sn + vendor_key` 签名，提交 `app_id + 门店激活码 + 全局唯一 device_id` 调激活接口，拿到 `terminal_sn + terminal_key`。之后的签到、支付、查询、退款都用终端参数签名。
- 【已核实】"一个密钥每个自然日会过期"，需要签到换新密钥。文档建议"每自然天执行第一笔核心支付接口调用时，自动执行签到操作"（https://doc.shouqianba.com/zh-cn/api/Q&A-技术-Web%20API.html ）。新版指南要求集群部署时"原子更新"密钥，并从共享库读取（https://open.shouqianba.com/docs/payment/106 ）。
- 【已核实】终端可以是纯服务端的："在商户没有终端的情况下，直接在服务器管理终端号和终端密钥……开发者可以选择所有支付都算作一个终端发起的请求，也可以采用'前端1->收钱吧终端1，前端2->收钱吧终端2'的方式。后者的好处在于便于商户日后在商户系统中对账。"（同上 Q&A）
- 【已核实】签名方式：`sign = MD5(body + key)`，请求头写 `Authorization: {sn} {sign}`。所有金额以分为单位，所有返回值都是字符串（https://doc.shouqianba.com/zh-cn/api/sign.html ， https://open.shouqianba.com/docs/payment/93 ）。不需要 API 证书。

### 2.2 扫顾客付款码（B扫C）

- 【已核实】接口 `POST /upay/v2/pay`（https://open.shouqianba.com/api-docs/payment/140 ）：
  - 必填参数：`terminal_sn`、`client_sn`（商户订单号，≤32 字节，商户系统内唯一）、`total_amount`（分）、`dynamic_id`（付款码内容）、`subject`、`operator`。
  - `payway` 可以不传，"支付平台会自动根据支付码识别支付方式"。
- 【已核实】结果处理："如果pay同步返回的order_status不是最终状态，需要马上发起轮询（调用查询接口）。轮询间隔3~5s，总时长控制在40~50s"。"支付失败订单的二次支付请求，请上送新的商户系统订单号"（同上）。
- 【已核实】超过查询窗口仍无最终状态时，订单标记为"结果未知"，提示收银员不要再次扫码扣款（https://open.shouqianba.com/docs/payment/83 ）。旧版 Q&A 的说法是：轮询窗口内仍非最终状态就调撤单（cancel），"该动作类似于POS机的冲正"。

### 2.3 生成二维码让顾客扫（C扫B）

- 【已核实】聚合二维码接口 `POST /upay/support/precreateQrcode`（https://open.shouqianba.com/api-docs/payment/146 ）：
  - "生成不落单的付款二维码短链"，"本接口不创建真实订单"；
  - 返回 `qr_code`（短链）和 `qr_code_image_url`（二维码图片直链）；
  - 二维码 15 分钟有效，顾客扫码后的实际支付 4 分钟有效（https://open.shouqianba.com/docs/payment/96 ）。
- 【已核实】预下单接口 `POST /upay/v2/precreate` 的返回里有 `qr_code`。新版指南写的支付有效期是 4 分钟（https://open.shouqianba.com/docs/payment/80 ）。旧版 Q&A 一处写"约为90秒"，另一处写"有效期：4min"，两处前后矛盾，以新版为准。
- 【推断】前台收银屏展示动态码这个场景，用聚合二维码接口或 precreate 都可以。哪个更合适，要等实际调用后再看回调里能拿到的字段。

### 2.4 回调与订单关联

- 【已核实】支付回调（https://open.shouqianba.com/api-docs/payment/145 ）：
  - 由收钱吧 POST JSON 到我们的地址，请求头 `Authorization` 里是 RSA SHA256WithRSA 签名，用收钱吧公钥验签（公钥"可在 API 调试台查看并复制"）；
  - 重试间隔为 1s、5s、30s、600s；
  - 收到后返回字符串 `"success"`。
- 【已核实】`notify_url` 是请求参数，在 pay、precreate、聚合二维码等接口上都可以按单传（https://open.shouqianba.com/api-docs/payment/140 ， https://open.shouqianba.com/api-docs/payment/146 ）。
- 【已核实】回调和查单都会带上 `client_sn`（我们的订单号）、`sn`（收钱吧订单号）、`trade_no`（微信或支付宝的订单号）、`reflect`（原样透传，≤64 字符）。可以用它们把收款对到订单上。
- 【已核实】官方推荐的做法是"主动轮询加回调"，两者共用一个状态机，做幂等处理（https://doc.shouqianba.com/zh-cn/api/interface/precreate.html ， https://open.shouqianba.com/docs/payment/77 ）。
- 【已核实】回调文档只写了"消费者支付成功或失败"，**没有提到退款回调**。退款结果要靠同步返回或查单拿到。

### 2.5 补充：把订单推到收钱吧设备上收款

- 【官方文档，未实测】如果店里有收钱吧 T9 一类的专用收款设备，可以调用 `/appPush/tradePush`，把订单号和金额推到设备上，由设备完成收款，结果回调到我们的 `notify_url`（https://doc.shouqianba.com/zh-cn/api/interface/MIS.html ）。
- 【推断】这样前台不用另配扫码枪，收银员在收钱吧设备上收款，订单金额由我们系统下发。前提是店里有这类设备【需店主确认】。

## 3. 能否拿到付款人的稳定标识（识别回头客）

### 3.1 收钱吧返回什么

- 【已核实】pay 和回调里有两个字段：
  - `payer_uid`："支付平台（微信，支付宝）上的付款人ID"；
  - `payer_login`："支付平台上(微信，支付宝)的付款人账号"。
  两个字段都是**非必填**（https://open.shouqianba.com/api-docs/payment/140 ）。
- 【已核实】旧版查询接口文档写得更具体（https://doc.shouqianba.com/zh-cn/api/interface/query.html ）：
  - `payer_uid`："订单付款人的id，微信对应sub_openid"，示例：微信 `oGFfks...`，支付宝 `2088452294453691`；
  - `payer_login`："订单付款人信息，微信对应openid"，示例：支付宝 `bren*@icloud.com`（脱敏账号）。
- 【已核实】pay 接口的 `extended` 参数说明里写着"指定上送appid获取用户身份标识"，示例 `{"sub_appid": "wx..."}`（https://open.shouqianba.com/api-docs/payment/140 ）。

### 3.2 微信侧的含义

- 【已核实】微信服务商版付款码支付（https://pay.weixin.qq.com/wiki/doc/api/micropay_sl.php?chapter=9_10&index=1 ，更新于 2026.04.24）：
  - `openid` 是"用户在商户appid 下的唯一标识"，这里的 appid 是**服务商**的 appid；
  - `sub_openid` 是"子商户appid下用户唯一标识，如需返回则请求时需要传sub_appid"；
  - `sub_appid` 必须与 `sub_mch_id` 绑定。
- 【推断】把这两份文档合起来看：
  - **不传 `sub_appid`**：大概率只能拿到 `payer_login` = 收钱吧服务商 appid 下的 openid。这个值对"同一个服务商 appid"是稳定的，可以识别回头客，但它属于收钱吧的 appid，我们拿它调不了任何微信接口。另外，如果收钱吧把这家店的微信通道换到别的服务商或收单机构，这个值就会变。
  - **传 `sub_appid`**（比如我们自己的公众号或小程序 appid）：可以拿到 `payer_uid` = 我们 appid 下的 sub_openid，以后小程序和会员体系都能复用。前提是这个 appid 已经和店里的特约商户号完成绑定，这需要收钱吧这个服务商来配置【需向收钱吧对接人确认】。
- 【未找到】文档没说"付款码查询 openid（不扣款）"这类能力收钱吧有没有对应接口。#7 里提到的微信 `authcodetoopenid` 能力，在收钱吧 API 里找不到。

### 3.3 支付宝侧

- 【已核实】收钱吧说支付宝走的是"支付宝当面付2.0接口协议"（Q&A）。查询示例里支付宝的 `payer_uid` 是 2088 开头的 user_id。
- 【推断】#7 已经核实：支付宝对新应用逐步回收 `buyer_user_id`，改发 `buyer_open_id`。收钱吧的支付宝应用今后返回哪一种、是否稳定，文档没写，需要实测。

### 3.4 小结

能拿到付款人标识，但字段是"可选"返回的，口径（属于哪个 appid）取决于收钱吧的通道配置。**必须用真实交易实测**：同一个微信号在不同天付两次款，对比 `payer_uid` 和 `payer_login` 是否一致、是否有值。

## 4. 退款、对账单能否通过接口获取

### 4.1 退款与撤单

- 【已核实】退款接口 `POST /upay/v2/refund`（https://doc.shouqianba.com/zh-cn/api/interface/refund.html ）：
  - 需要 `refund_request_no`（防重复退款，不能复用）和 `refund_amount`，用 `sn` 或 `client_sn` 定位原单；
  - 支持多次部分退款，"可操作至剩余金额为0"，"三个月以内都可以进行退款"；
  - 手续费"按照退款金额占订单金额比例系数乘以订单总手续费进行手续费退还"。
- 【已核实】撤单只能在"当天"做一次，全额退回，"包括支付手续费"；"进行过退款的订单不能撤单"（Q&A）。
- 【已核实】**微信退款权限有坑**：
  - 原文："现新签约的微信正式商户（即是微信支付特约商户），默认都是没有退款权限的……需要将退款权限授权给服务商（即收钱吧）"；
  - 操作路径："特约商户超级管理员登录商户平台 → 产品中心 → 我授权的产品 → 找到我的服务商 '1238313502喔噻互联网科技有限公司' → 服务商API退款授权 → 点击授权"；
  - 来源：https://doc.shouqianba.com/zh-cn/api/interface/refund.html 。
- 【推断】这一点也从侧面说明，至少一部分收钱吧商户的微信通道是"收钱吧（喔噻）作为服务商 + 商户作为特约商户"的结构，见第 5 节。

### 4.2 对账单与手续费

- 【未找到】收钱吧移动支付 API（新版 9 个接口和旧版全部接口）里**没有对账单或结算单下载接口**，交易响应字段里也**没有手续费字段**。
  - 有的金额字段是 `total_amount`、`net_amount`（扣掉退款后的剩余）、`settlement_amount`（本次操作金额）；
  - 查询接口返回的 `payment_list` 是"活动优惠"，不是手续费。
- 【已核实】官方对对账的提法都指向商户后台：
  - Q&A 里说多个终端"便于商户日后在`商户系统`中对账"；
  - 官网写着"支持远程查账对账……并可根据财务要求定制对账单"（https://www.shouqianba.com/ ）。
- 【推断】我们系统能通过 API 拿到的是**逐笔交易**（同步返回、回调、查单），可以按天自行汇总"本系统发起的收款"。**按日结算明细、手续费、到账金额**只能由店主从收钱吧商户后台或 App 导出，再导入我们的系统核对。要不要做导入，等看到导出格式再定【需店主确认】。

## 5. 店主的微信支付商户号和收钱吧是什么关系，还能不能直接用微信官方接口

### 5.1 微信的两种模式

- 【已核实】微信支付"接入模式"对比（https://pay.weixin.qq.com/doc/v3/partner/4012081931 ，更新于 2026.06.01）：
  - 普通商户模式：资金"直接结算到商户自己的结算账户"，商户自己持有 API 证书和密钥。
  - 服务商模式：资金结算到子商户账户，"服务商账户不直接收款"。API 证书"仅服务商持有，子商户不需要；代调用时以服务商身份签名"，APIv3 密钥"子商户不设"。用户标识是 `sp_openid` 或 `sub_openid`。
- 【已核实】在服务商模式下，交易都是服务商带着 `sub_mch_id` 发起的（同上；服务商版付款码文档里 `mch_id` 是"服务商号"，`sub_mch_id` 是"子商户号"）。

### 5.2 收钱吧在其中的角色

- 【已核实】收钱吧文档把它的微信商户称为"微信支付特约商户"，服务商是"上海喔噻互联网科技有限公司"，服务商商户号 1238313502（Q&A 和退款文档）。
- 【推断】如果店里的微信收款就是这个结构，那么：
  - 店主名下的是一个**特约商户号**。店主可以登录微信支付商户平台查账、给服务商授权，但没有自己的 API 证书和密钥，**我们不能拿这个特约商户号直接调微信官方接口**。调用方只能是服务商（收钱吧）。
  - 要走 #7 的直连方案，需要用同一张营业执照**另外申请一个普通商户号**（个体户可以申请，#7 已核实）。这样资金、费率、对账都和收钱吧分开，变成两套。
- 【推断】收钱吧也可能通过银行或支付机构（收单机构）给商户开微信通道，这时商户号由收单机构的渠道体系管理，结构和上面不同。**这家店属于哪种情况，文档推不出来**，必须由店主核实（见第 7 节第 2、3 题）。
- 【未找到】收钱吧有没有开放"由第三方 ISV 以自己的 sub_appid 绑定到收钱吧特约商户"的流程，文档没写，只在小程序支付场景提到"正式商户和目标小程序`appid`的关系必须配置完成"（https://open.shouqianba.com/docs/payment/80 ）。

## 6. 和 #7"微信付款码 V2 + 支付宝当面付直连"方案的对比

| 维度 | 走收钱吧 API | 直连（#7 方案） |
|---|---|---|
| 准入 | 找收钱吧对接人拿 vendor 参数（提供企业信息），门店在后台生成激活码；不能自助 | 店主自己申请微信普通商户号、支付宝当面付；可以自助，但要另开商户号 |
| 资金与费率 | 沿用现有收钱吧签约（费率、结算周期不变），和店里其他收钱吧码牌、设备的流水在一处 | 新商户号单独结算，费率按微信、支付宝官方标准（#7：0.6%–1% / 0.6%）；和收钱吧的流水分成两处 |
| 支付方式覆盖 | 一套接口覆盖微信、支付宝、云闪付等，`payway` 自动识别 | 微信、支付宝两套接口，各自签名、各自证书 |
| 开发量 | JSON + MD5，无证书；但要管终端激活、每日签到换密钥 | 微信 V2 XML + MD5/HMAC，撤单要双向证书；支付宝 RSA2；可以用社区库 gopay |
| 回头客识别 | `payer_uid` / `payer_login` 可选返回；不传 sub_appid 时只有收钱吧 appid 下的 openid（推断）；要实测 | 在自己的 appid 下拿 openid / buyer_open_id，口径清楚、自己掌控；还能用"付款码查 openid" |
| 退款 | 有 API；微信退款要店主先给收钱吧服务商授权 | 有 API；微信退款要证书 |
| 对账 | 无对账单 API，结算和手续费去收钱吧后台导出 | 微信、支付宝都有官方对账单下载接口（本文未复核） |
| 多租户（SaaS） | ISV 一次接入，任何收钱吧商户提供激活码即可，对已经用收钱吧的门店门槛低 | 每家店要有自己的商户号，并把密钥、证书交给我们；或者我们申请成为微信服务商（必须是企业主体，#7/本文已核实） |
| 依赖 | 依赖收钱吧对接人、收钱吧接口的稳定性；通道变化可能影响 openid 口径 | 只依赖微信、支付宝官方 |

【推断】取舍建议（供"收款方案"决策参考，不是定论）：

- 如果店主**不想多开商户号、想让流水留在收钱吧**，走收钱吧 API 更顺。代价是回头客识别要先实测，对账要靠导入后台导出的文件。
- 如果**回头客识别（openid）是硬需求**，并且实测发现收钱吧拿不到稳定的标识、也绑不了我们的 sub_appid，那么直连更可靠。
- 两者也可以并存：先用收钱吧 API 收款，同时实测 openid。代码层面把"收款通道"做成可替换的接口。

## 7. 需要店主确认的问题

1. **收钱吧商户后台或 App 里，门店下能不能生成"激活码"？** 文档说激活码"需要在商户平台门店下生成"。
2. **有没有微信支付商户平台（pay.weixin.qq.com）的登录权限？** 如果有，请在"产品中心 → 我授权的产品"里看看服务商是不是"喔噻互联网科技有限公司 / 1238313502"，再看看"服务商API退款授权"有没有开通。
3. **顾客微信支付后的账单详情里，"商户全称"显示的是什么？** 这能帮助判断微信通道挂在谁下面。最好截一张图。
4. **收钱吧签约的费率和结算方式**（T+1、D0、手续费由谁承担），在收钱吧 App 里查看。
5. **店里用的是哪些收钱吧设备**：码牌、扫码王、智能 POS（如 T9）、手机 App？决定能不能用"订单推送到设备"。
6. **收钱吧后台能不能导出每日对账单或结算明细？** 导出格式是什么（Excel/CSV）？有没有手续费列？请导出一份样本。
7. **有没有收钱吧客户经理或对接人的联系方式？** 申请开发者参数需要通过他们。
8. **店里有没有自己的微信公众号或小程序 appid？** 如果有，可以请收钱吧尝试绑定成 `sub_appid`，用来拿我们自己的 openid。
