## 背景

- 店主在中国经营一家综合烫染店，6–15 人。
- 路线：先服务自己的店 → 做成自有产品 → SaaS 商业化，**闭源商用**。
- 开发方式：店主 + AI 编程助手。

## 已定

| 决定 | 理由 |
|---|---|
| Go 从零开发：Echo、sqlc + pgx、goose、shopspring/decimal、PostgreSQL（行级安全隔离门店）、Nuxt + Nuxt UI、wechatpay-go；小程序后期用 uni-app | 全部 MIT / Apache / PostgreSQL 协议，可闭源商用；微信支付有官方 Go SDK；代码量小，AI 好掌控 |
| 不复用 mms 代码，只借鉴设计思想 | mms 是 AGPL-3.0，闭源 SaaS 不能用；借鉴的只是通用做法（流水记账、快照、只追加审计） |
| 不用芋道 | MIT 但体量大、Java、无美发业务；首版需要的基础设施有限 |
| 不用 Dify / FastGPT 做 AI 核心 | 其许可证禁止未经授权运营多租户服务 |
| 不自部署开源换发型模型 | HairFastGAN 内含禁止商用的组件 |
| 不用人脸识别认顾客 | 《人脸识别技术应用安全管理办法》合规成本高于收益 |
| AI 比重要高于下方"旧 P0" | 店主明确要求：AI 原生是核心差异，不是 P1 附加功能 |

## 设计原则

1. **数据来自员工本来就必须做的事**（开单、收银、售后、轮牌），不依赖自愿录入。
2. **不用员工自愿提交的数据评价员工自己的工作**（照片只挑好的拍）。
3. **让记录对记录的人有利**：开单 = 登记自己业绩；占位 = 保护自己时段；返工不自动扣提成。
4. **账务确定性**：余额由流水推出，不直接改余额；撤单写反向记录；下单时快照项目名、规格、提成。
5. **AI 理解、提醒、解释；动钱的操作走确定性业务接口**（此条在提高 AI 比重后需要重新审视边界，见下文）。

## 业务设计要点

- **到店接待是流程中心**。来源：线上预约、发型师私约（微信）、熟客直接来、路过散客、团购到店、朋友带来。预约只是可选的前置信息。
- **轮牌 / 点客**：平板显示轮牌队列；跳过须选原因并留痕；月底可查各人接客数。
- **占位**：发型师一键登记私约；该时段不被轮牌分走，顾客到店自动算点客。
- **项目 + 规格**：定价规格（长度、药水档次，影响价格）+ 记录规格（色系、卷型，烫染护理必选，3–5 个选项 + 其他）。
- **开单在服务开始前**：发型师开单、当场与顾客确认价格，前台只收款；中途可加项目。
- **多人分业绩**：一单可关联主发型师、助理等多个贡献；"谁做了什么"与"提成怎么算"分开；提成规则带版本和生效日期。
- **售后单**：必须关联 N 天内原单；类型（修补 / 重做 / 部分退款 / 全额退款）+ 原因；店长确认；记录返工人员和耗材；不自动扣提成。可对外承诺"烫染 N 天内不满意免费修补"。
- **质量信号**：返工、改价、退款、差评、新客是否回第二次（只给老板看趋势，样本少不下结论）。
- **卡项**：储值、次卡、套餐；付费储值与赠送金分开记账，退款规则不同。
- **顾客标签**：30–40 个、按服务类型只显示 6–8 个；每个标签标来源（顾客自述 / 员工观察 / 系统推断）和日期；默认值是"未知"而不是"无"；措辞按"顾客可能看到"来写；会过期。安全类（过敏、头皮敏感、近期烫染）优先。
- **照片**：只作为作品集；可选"烫染前存证照"（仅高风险项目，待店主判断）；存档同意与发布同意分开。
- **识别回头客**：微信付款码收款返回的 openid（商户内固定），无需顾客留信息；用于扣余额时须二次验证。
- **线下收款**：所有收款走门店码 / 扫码枪并关联订单；现金登记；每日三方对账（系统应收 / 实际到账 / 现金）。
- **断网**：首版不做离线功能，用 4G 备用网络 + 纸质补录（补录单标记）。
- **触达渠道**：企业微信（客户归门店）、小程序订阅消息（一次授权一次发送）、短信。

## 旧 P0 范围（AI 比重提高前的版本，待重新规划）

1. 门店、账号权限、审计
2. 服务项目与规格、员工
3. 到店接待、轮牌点客、占位预约
4. 服务单：开单报价、加项目、多人分业绩
5. 收银与卡项：多支付方式、储值 / 次卡流水、赠送金、撤单
6. 售后单
7. 报表与对账

旧 P1：微信支付（含 openid 识别）、顾客标签、AI 功能、小程序。

## 被否决的想法

| 想法 | 否决原因 |
|---|---|
| 发型师每单语音记录服务小记 | 员工忙、靠提成、流动大，不会稳定执行 |
| 照片识别作为顾客档案主要来源 | 发型师只拍做得好的，数据有偏 |
| 前台咨询偏好作为可靠数据 | 顾客说"没偏好"不代表没有；行为比口头可靠 |
| 每种款式单独建收银项目 | 项目数量爆炸 |
| 返工开 0 元单 / 不记录 | 无关联、可被滥用 / 数据丢失 |
| AI 动态生成角色工作台 | 6–15 人店固定角色页即可 |

## 待决问题

- **AI 比重提高后**：AI 是主要操作方式还是辅助？业务接口是否从第一天按"AI 可调用工具 + 草稿 → 确认"设计？AI 可直接执行与必须人工确认的边界？P0 放哪些 AI 功能？选哪家模型、成本、断网降级？
- 注意："语音记录被否决"针对的是**员工额外自愿录入**；若语音是**开单本身的操作方式**（替代点按钮），属于不可回避环节，需重新评估。
- **店里真实规则**（只能由店主提供）：提成与轮牌规则、卡项种类、赠送金政策、退卡政策、售后期限、各烫染项目的阶段与时长、现用收银系统（决定数据迁移）。

## 未验证的假设

- 上述 Go 技术栈组合未做 PoC。
- 大模型在美发场景调用工具的稳定性、中文语音在店内噪音下的识别率。
- 微信付款码 openid 方案的实际接入（需商户号）；支付宝是否有类似能力未查。
- 免费日历组件（schedule-x、vue-cal）是否支持按员工分列未验证；FullCalendar 资源视图需付费。
- 最高法预付式消费司法解释：已核实第一条列举"理发、美容"、2025-05-01 施行；"7 日无理由退款"等具体条款未对照原文核实。
- 上线需 ICP 备案。
