# AI 提醒：店里的事和时间点触发提醒规则，AI 只负责写和起草，规则先观察再开

店主要的是工作上的 personal agent：不等人来问，AI 自己盯着店里的事，到点提醒该管的人，能起草的先起草好，人点头就行（2026-11-27）。本 ADR 定下它怎么被触发、提醒谁、能做到哪一步。依据见两篇调研：

- [主动 agent 调研](../research/2026-11-20-proactive-agents.md)：规则决定触发、先观察后放权、打扰的代价大于漏帮一次；
- [开源 personal agent 调研](../research/2026-11-27-open-source-personal-agents.md)：模型之前有一道确定的门、确定性去重键、冷却、次数和过期参数、失败不静默也不刷屏。

店主已于 2026-11-27 确认以下做法；标注"可设置"的是门店设置（[ADR-0002](0002-business-rules-are-per-store-settings.md)）。

- **谁决定要不要提醒：规则，不是模型。** 判断标准是"一句话能说清、不用说'看情况'的就是规则"；说不清的第一版不做。每条提醒规则是一段写死的检查，例如：
  - 明天有预约的顾客；
  - 昨天还没日结（日结只能结今天以前的营业日，所以第二天早上查昨天）；
  - 60 天没来的老顾客。

  规则由两种东西触发：
  - 店里发生的事：业务操作成功后，在同一事务里留下事件，例如结账、建预约、充值；
  - 时间点：门店营业日里的固定时刻，像工资自动锁定那样定时检查。

  规则没选中任何对象，就不叫醒模型。模型不轮询数据，也不判断该不该打扰人。
- **AI 做什么：写成人话、起草。** 规则选中一件事后，AI 用收件人本人的权限把它写成一条 AI 提醒；需要动手的，顺带起草一张草稿，例如回访话术、预约提醒、日结草稿。
  - 草稿仍走 [ADR-0004](0004-p0-ai-drafts-writes-human-confirms.md) 和 [ADR-0008](0008-ai-drafts-stored-confirmed-and-expire-same-day.md)：发起人记为收件人本人，当天有效，人确认后才生效。
  - 金额、次数、日期、单号这类事实由代码直接显示，不经模型转述；AI 写的话在界面上和事实分开，标明是 AI 写的。AI 写的话里出现了规则没给的数字，就改用固定文案。
  - 模型调用失败时不吞掉提醒，改发规则自带的固定文案，只是不带草稿。
  - AI 提醒本身不改任何业务数据。
- **提醒谁：按权限和关系，每人只收自己的。** 规则写明收件人怎么选，例如"有日结权限的人"、"这位顾客的负责发型师"。收件人看不到的数据不出现在提醒里，权限与 AI 对话相同（[ADR-0009](0009-roles-and-permissions.md)）。老板不代收员工的提醒。
- **先观察，再开（照 DeepSeek Super-agent 的 observe 模式）。** 每条规则有三档：关、观察、开（可设置，新规则默认观察）。
  - 观察时只记下"本来会提醒谁、说什么"，只给老板看，不打扰任何人。
  - 没发出去的也要记下原因：规则没选中、被去重、到了每日上限。这样老板问"为什么没提醒我"有答案。
  - 给老板看的是一张汇总：这条规则过去几天触发了几次、每人每天几条、去重和上限拦下了多少，再抽几条样例文案，每条可以点"有用 / 没用"；不要求老板翻原始记录。
  - 老板看过，觉得有用、不吵，再改成开。
  - 同一条规则的提醒连续被忽略若干次（可设置），自动退回观察。
- **不吵。**
  - 同一规则、同一收件人、同一对象、同一营业日最多一条，重复的直接视为已提醒。观察档的记录和开启后的提醒各算各的，当天从观察改成开，照样能发出去。
  - 同一对象再次提醒前要隔几个营业日、最多提醒几次、过了多少天不再提，这三项每条规则各自可设置。
  - 不急的事合并成一张简报（例如发型师早上的回访清单、老板早上看的昨日日结简报），一张简报只算一条。
  - 每人每天的条数有上限（可设置）。"不马上处理就会损失钱"的提醒（例如团购券核销后快到不能撤销的时限）不占这个上限，但仍按上面的规则去重。
  - 提醒对应的情况已经不在时（例如日结已经做了、顾客今天已经到店），提醒自动失效，不再显示。草稿确认时照常按当时的数据重新检查，情况变了就不执行。
  - AI 提醒放在各人每天一定会打开的地方：后台首页和日结页、员工小程序首页，以及待确认、AI 面板；不只放在一个要专门点开的通知列表里。第一版不往微信、短信、公众号推送。
- **出错时让老板知道，但不刷屏。** 规则检查连续失败到一定次数才提示老板；同一个问题一天最多提示一次。
- **发给模型的东西去掉姓名和手机号**（店主已同意的口径）。规则只带上记录编号，AI 起草时再按编号读。

## Considered Options

- **让模型定时把店里的数据看一遍，自己决定提醒什么**（OpenClaw 原来的心跳、Letta 的自管理定时）：未被采纳。
  - 每次都要把大量数据发给模型，贵且慢。
  - 同样的情况今天提醒、明天不提醒，没法测试，也说不清为什么打扰了人。
  - OpenClaw 自己后来也把心跳降成了普通定时任务。
- **让模型回一个"无事"暗号，或者再用一次模型判断要不要通知**（Hermes `[SILENT]`、Khoj）：未被采纳。
  - 这时已经花了一次模型调用。
  - 暗号被模型写歪就会变成一次打扰。
  - Khoj 判断出错时默认通知，与"宁可少打扰"相反。
- **照 Pi（earendil-works/pi，原 badlogic/pi-mono，MIT）的扩展事件来做**：未被采纳为主体。
  - Pi 的 `pi.on(...)` 事件是智能体自己一次对话的生命周期（session_start、tool_call 等），解决的是"拦住一次工具调用"；这件事我们已经由操作层的权限检查和草稿确认承担。
  - 它的进程内事件总线 `pi.events` 不跨请求、不落库。
  - 可借鉴的是"规则挂在事件上、处理器可以拦下"的写法。
- **让 AI 自己积累对店里和员工的了解，改自己的记忆和规则**（Hermes、Letta）：未被采纳。老板看不见也查不了。我们只统计人对每条规则的提醒是忽略、修改还是确认，给老板看，由老板改规则。
- **AI 发现问题后直接改数据**：未被采纳，理由同 ADR-0004。

## Consequences

- 需要一张业务事件表，在业务操作的同一事务里写入，事件不会比数据先到，也不会丢。操作日志已覆盖大部分写操作，事件表可以先从它取，不够再加。
- 需要一个按门店的定时检查，复用工资自动锁定的做法：
  - 多个服务实例或上一轮还没跑完时，同一门店同一规则不重复跑；
  - 重启后重跑当天的检查不会重复提醒；
  - 过了营业日的不补发。
- 需要提醒规则表，存档位、参数和规则版本。规则要记住"上次的值"时（例如日结差额变化），这个值和提醒在同一事务里一起写入。
- 需要 AI 提醒表，存收件人、规则和版本、对象、营业日、内容、关联草稿、已读、失效、人怎么处理的。以"规则 + 门店 + 收件人 + 对象 + 营业日"做唯一约束，观察和开启各一份，作为去重的依据。每次检查的结果和没发出的原因另存一张只追加的记录表。
- 同一门店的检查一次只跑一轮（按门店加锁，不按规则），这样几条规则不会同时读到"今天还没满上限"而一起超过上限。去重、冷却、次数、过期和每日上限从第一条规则起就生效，观察汇总里的"拦下多少"才是真实数字。
- 第一批规则应挑本店真实会用、能验证的几条，并用双轨营业日的数据检验观察记录是否有用。按[功能清单](../feature-catalogue.md)里本店一年的数据，本店不用预约、不做库存，这两类提醒不进第一批。候选（待店主挑）：
  - 老板：第二天早上的昨日日结和异常简报：昨天没日结就提醒去日结；已日结的报差额（差额要等人填完实际到账才有）；再加上昨天的删单、手工调卡、改单、开卡充值没选业绩归属人；
  - 前台和助理：团购券核销后还没关联单据（抖音验券超过一小时不能撤销）；
  - 发型师：早上的老顾客回访清单，优先列自己名下次卡或套餐有余量、很久没来的顾客，每天只列两三位，附回访话术；
  - 老板和员工：月底锁定工资表之前的检查，列出漏打卡、没关联的单据，员工只看到自己的。
- 第一批不能全是给老板盯员工的提醒（谁删单、谁改价），要同时有帮员工的（回访清单、提成核对），否则员工会把它当成监工。
- 以后要往微信或小程序推送、或者让某条规则不经确认直接执行，都要另写 ADR。
