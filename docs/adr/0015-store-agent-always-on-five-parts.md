# 门店 AI 照 Anthropic always-on 的五个组件搭：事件系统、定时器、记忆、权限、通知

店主 2026-11-27 认可了这套架构，要求照 Anthropic《[Building always-on agents](https://claude.com/resources/articles/building-always-on-agents)》做，尽量不改原文，只在两种情况下改：不改就会在我们这里出问题，或者原文没说到。依据见[五篇资料调研](../research/2026-11-27-agent-architecture-readings.md)和[企业 agent 架构调研](../research/2026-11-27-enterprise-agent-architecture.md)。

本 ADR 取代 [ADR-0012](0012-ai-reminders-rule-triggered-observe-first.md) 的"要不要提醒由规则决定，不由 AI 决定"：以后由门店 AI 在运行里判断要不要说、说给谁。ADR-0012 的去重、冷却、观察档并入通知这一块。

## 照原文的部分

- **事件系统**：
  - 一张持久的事件表，按来源编号去重；写事件的地方只做轻量检查，较深的检查放到运行里。
  - 每个收件箱同时只有一个 worker；worker 崩了，换一个照样能重试。
  - 接着之前的事接回原会话，其他事新开会话。
  - 运行中途来的事不打断正在跑的运行：员工收件箱合成下一次运行，门店收件箱攒成一批。
- **定时器**：分跟进和周期两种，单独一张表。到点只往收件箱写事件，从不直接启动运行。
- **记忆**：一组文件存在数据库里。`instructions.md`、`index.md`、`reported.md` 每次都加载，`notes/`、`progress/` 按需读；只存查不回来的东西。
- **权限**：
  - 员工的运行用本人权限，改数据走草稿（ADR-0013），草稿就是原文的"挂起"，确认或拒绝作为事件回到收件箱。
  - 不改数据、但风险较高的直接动作先过分类器：给员工发 AI 提醒、写门店规矩、定跟进。
- **通知**：用正式发件箱，一张外发表加一个派发器，因为我们要控制节奏。一次运行三种结局：发、不发、挂起。先安静。

## 必要改动

1. **两种收件箱：门店一个，员工每人一个。** 原文是替一个人干活的，我们替门店干活。门店收件箱收业务事件、门店的定时器和员工交回的结论；员工收件箱收他本人的对话、回答和门店交办给他的事。
2. **收件箱之间只传编号和结构化字段，不传文字。** 门店运行用老板权限，文字可能带出员工不该看的东西，也可能夹带指令借老板权限执行。交办和回答都带交办编号，对不上编号的回答不接；改交别人以后，原来那位晚到的回答作为新事件交门店核对。
3. **门店运行用老板角色，不绑某位老板的账号。** 门店不是一个人，没有"本人"。门店运行不直接给员工发 AI 提醒，只往员工收件箱交办，由员工的运行用本人权限去写；门店运行起的草稿，发起人记为"门店 AI"。

## 原文没细说、我们补的

- **转交**：交办出去的同时定一个跟进，到点没人处理，就再提醒、改交当班的另一位同岗位的人，或者交给店长。等多久、找谁是门店设置。
- **通知分三档**：立即送到、并入当日简报、并入每周简报。由 AI 选档，分类器复查"立即"是不是真的急。同一件事只留一条：还没发就替换，已经发了就接在原来那条下面，事办完了就撤回。

## Considered Options

- **门店一个收件箱，或者只有员工收件箱**：都没采纳。只有门店收件箱，员工各自的对话会互相排队；只有员工收件箱，"券核销后没人关联"这类不属于任何一个人的事就没地方放。
- **收件箱之间传文字**：未被采纳，理由见必要改动 2。
- **每次变化都发一条**：未被采纳，会变成噪音（店主 2026-11-27）。

## Consequences

- 搭建顺序：
  1. 先只做"团购券核销后半小时没关联单据"一件事，五个组件各做最小的一份；
  2. 当日、每周简报，现有的 AI 提醒代码换成这套；
  3. 员工对话进收件箱；
  4. 员工记忆；
  5. 更多事件；
  6. 微信推送、dreaming、跨店。

  店主定：全部做完再进双轨营业日。
- 员工对话从"等一个请求返回"改成"发出去、等推送"（第 3 步）。
- 草稿的发起人要允许为空，表示"门店 AI"；系统里已有自动锁工资月的先例。
- 分类器的每次判断都要记下来，作为调档位和条数的评测数据。
